- Agent keys: scheduled agents use `/functions/v1/mcp-agent` (hand-written gateway, verifies `ytp_agent_` key) which forwards to the SDK-generated `mcp-agent-core` (src/lib/mcp/agent-entry.ts, same tools via toolset.ts). Why: @lovable.dev/mcp-js only supports OAuth issuer auth.
- src/lib/mcp must use relative imports only (no `@/`). Why: the edge bundler turns `@/` into broken `npm:` specifiers.
- Per-version context (Google Maps routes, Exact Itinerary PDF, pvp_override) lives in `lead_versions`; `leads` only mirrors the LIVE version. Why: versions must be fully independent while agents/KPIs still read `leads`.
- All FSE creation surfaces persist through `createOrFindFSE` before reporting success or selecting the supplier. Why: Costing and the FSE database must share duplicate-safe supplier, service, and link creation.
- JARVIS Live Map is a DB registry (agent_departments/agents/agent_tasks/agent_runs) rendered at /agents/dashboard; old Spark at /agents/spark-legacy. Why: one registry feeds map, counters and escalation; level ceiling enforced by trigger.
- Regions (PT+ES) live in `regions` + `region_destinations`; app reads them via `useRegions`, edge functions via `_shared/regions.ts`, suppliers link via `supplier_regions`. Why: new regions appear everywhere without code changes.
- Planner, public proposal and PDF derive inclusions through `proposalIncluded` from their current version's itinerary rows, ignoring legacy overrides. Why: one derivation prevents stale or truncated inclusions across outputs.
- Proposal cancellation defaults are resolved through `closingTermsI18n` using the selected itinerary's touring days, excluding accommodation day zero, while preserving custom terms. Why: editor, public proposal and PDF must share consistent deadlines.
- Planner direct PDF export captures a read-only clone of the current full preview using the shared printed PDF builder and size policy. Why: preserve unsaved version content and filename without publishing or opening print dialogs; bounded page captures avoid long-tour canvas limits.
- Client-facing links use `PUBLIC_APP_URL` (src/lib/publicUrl.ts) and readable slugs from `buildProposalSlug`; never the company's main website domain. Why: yourtoursportugal.com hosts the corporate site.
- Catalog execution versions live in product_local as independent plan/costing snapshots; template mode reuses lead editors without lead persistence, and imports copy execution rows into product_ref. Why: catalog edits must not mutate existing leads or trigger bookings, payments, or Calendar actions.
- Catalog add-ons share execution costing rows and retain explicit retail rates separate from supplier NET; productAddons calculates their pax totals. Why: optional retail offers must survive imports without inventing supplier costs or entering the base price before confirmation.
- Populated catalog executions retain the programme retail table in a catalogBasePrice row and mark unquoted service NET as pending; imports recalculate that row for lead passengers. Why: operational templates must not erase the published programme price or invent supplier costs.
- Bókun bookings enter via `bokun-poll` (pg_cron business/night modes, cursor in `bokun_sync_state`, shared logic in `_shared/bokun.ts`); `bokun-webhook` is kept inactive for Plus plans. Leads match by `bokun_confirmation_code` and skip unchanged `bokun_hash`; the NetHunt deal (official YT ID) is created by sync-worker entity `lead_create_deal`. Why: NetHunt owns the YT sequence, the account has no webhooks, and the integration never writes to NetHunt/Calendar directly.
- Workbench is additive and read-only toward external services; its checklist RPC updates auto rows only, and page approvals only record review without invoking execution. Why: preserve existing sync ownership, manual overrides and human control.
- Workbench UI, recompute and MCP share pure scope rules in the edge shared directory; archive status is derived, not persisted. Why: keep Lisbon dates and active filters consistent without stage mutations or new scheduled calls.
